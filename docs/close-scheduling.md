# 收盘调度与跨日恢复

定时首轮为北京时间17:23，重试为18:23，另在次日05:23进行补偿（周五收盘的补偿在周六）。GitHub schedule 可能延迟或丢弃；增加触发点不代表能保证准时执行。

## 目标日与恢复窗口

定时任务从 GitHub API 读取**原始 workflow run 的 `created_at`**，结合 `github.event.schedule`，选择不晚于该创建时刻的最近一次名义 cron 日期。三个 cron 都按 UTC 周一至五配置，目标评分日是该 UTC 日期对应的北京时间收盘日。runner 排队、`check` 运行耗时及 rerun 都不会改变该目标日。例如10月29日的首轮在北京时间10月30日00:17创建，仍处理10月29日。

GitHub 事件不提供最初计划执行的精确时间；若平台在下一个同类 cron 之后才创建任务，无法可靠追溯它属于哪个旧触发点。本流程不猜测任意历史日期，不承诺补齐所有历史空洞。

只有目标日属于已核验交易日，并且准备冻结在其15:00至**下一交易日09:30之前**完成，才允许消费报价源仍保留的真实收盘截面。每条报价仍必须注明目标日、落在既有15:00至18:00收盘时间约束内、价格有效且不在未来；不接受代码重复的混合截面。先验证再合并，禁止其他日期的报价污染冻结价格。正常发布保留原有90%报价和评分覆盖门槛，失败代码明确计数，不更改评分规则。

每批的 `score_date` 固定为目标日，`quote_at` 和逐股 `quote_ts` 保留原始真实报价时间，`prepared_at` / `built_at` 保留实际执行时间。未引入历史行情合成或财务口径变更。当前实时源与市场底表不能可靠重建下一交易日开盘后的完整旧截面，因此超出窗口时明确报告“漏更”，禁止拿次日价格标记成前日收盘，也不自动启动其他日期的全市场补算。

普通手工触发只处理当天收盘；盘中手工触发失败。普通代码 push 只运行检查，只有原有显式 `[run-close]` 提交约定可触发评分，本次修复提交不带该标记。

## 发布与结果

- 在准备阶段读取 `close-data` 最新分支 SHA，再读取该不可变提交的清单，避开可变 raw URL 的缓存。已有同日或更新的合格清单时，校验日期、计数、覆盖及索引/分片代码集合后幂等跳过。
- 原子发布逻辑仍拒绝回退或重复覆盖已有快照。发布步骤随后重新读取真实数据分支，确认目标日或更新日期的合格清单；不能仅依赖发布脚本退出码。
- `outcome` 作业使用 `always()`，对校验、准备、评分、发布依赖统一判定。仅已核验发布、已有合格快照或已核验非交易日允许成功。未知日历、准备错误、窗口过期、报价不足及评分/发布跳过或失败均不能显示整个定时流水线成功。
- Actions 摘要区分 `ready`、`already_published`、`non_trading_day` 和最终 `published`。准备失败时摘要记录目标日期与具体原因。
